# R18 题目要求与 CPU 交付核对

核对日期：2026-10-15。依据仓库 [PROBLEM.md](../PROBLEM.md) 的题面转写、现有源码及本轮验收记录。官方测试数据、Threshold、阈值统计粒度、LUT 文件格式及最终服务器配置尚未提供；以下是实现和本地证据的核对，不是官方通过结论。

## 逐项对应

| 题目要求 | 当前实现及检查 | 证据与边界 |
|---|---|---|
| 1024×768、RGB 三通道、每通道 8 位 | C++ `--competition` 检查解码源通道数、16 位标志及尺寸；普通研究入口允许其他尺寸 | 100 图清单及来源由严格验收脚本固定。运行库支持任意有效像素数，不能据此把任意输入称为比赛输入 |
| 四个完整 256³ LUT | 完整 LUT 读取器要求恰好 `256³×3` 字节；采用项目已定义的 RGB8 原始格式 | 题面只说整型，并未明确 LUT 节点位深/编码。若官方格式不同，需要输入适配层 |
| 四次独立且不同的映射 | `--competition` 要求四级，禁止研究用 `fit-r14` 单级复合；每个像素始终依次访问四个稀疏表 | 原始四 LUT 的 SHA 各异及拟合来源应由 manifest 核验。仅凭稀疏字节不能证明来源不同；不同原 LUT 近似量化后也可能相同，因此运行时不错误拒绝相同的稀疏表 |
| 每级 m³，17≤m≤33 | `--competition` 对四级分别检查 m；节点必须是 `m³×3` 个 uint8；JSON `stage_m` 列出每一级 | 一般运行库允许 m=2..256 供控制实验；这些非比赛尺寸不应作为提交模型。混合尺寸四级合法执行，旧 `m` 字段只代表首级 |
| 每级输入/输出均为整型 | 四面体内核使用序列化 Q16 轴表，每级执行 `(sum+32768)>>16` 后再查下一级 | 标量、AVX2、MADD、标量 gather、exact-float 各候选均参加独立 64 位重心 oracle 比较；exact-float 的中间算术有整数精确性范围证明，逐级输出仍为 RGB8 |
| 输出精度 ΔE < Threshold | 评价器使用题面 RGB 欧氏距离，输出每图及全色的 mean/RMS/p99/max；阈值和作用范围显式输入 | 内核逐字节一致只证明执行正确，不证明稀疏近似达到未知官方阈值。示例 mean<2.0 不能替代官方判定 |
| 处理 100 张图、完成四级后的平均耗时 | `bench` 保留每轮完整图集 wall time 和 copy/apply 分项；严格脚本固定 100 图、四级、模型与二进制 SHA | 正式排名看完整轮次，避免用逐图 best-of-reps 均值。拟合、模型加载、解码及编码排除于 steady set 时间，并单列相关字段；官方是否包含这些阶段尚待明确 |
| 允许 SIMD、多线程等加速 | 真实 CPUID+OSXSAVE+XGETBV 检测后才启用 AVX2；只在独立 TU 使用 AVX2 编译选项 | 本机是原生 Windows 的 AMD Ryzen 9 8945HX，16 核/32 逻辑线程；不能把本机结果当作题面举例的 i7-14700 或正式服务器结果 |
| 内存、架构和移植可行性 | C++17 核心；OpenMP、AVX2、C++ SIMD、Zig、Rust 可选；不使用全局 `-march=native`；缺少加速后端时回退标量 | R18 已实际构建所有可选项关闭的版本并通过完整 CTest。其他 OS/ISA、编译器和移动设备尚未实测；磁盘格式当前按 little-endian 约定 |

## CPU 调度和内存边界

`apply_chain_batch` 接受不连续、不同长度的 RGB 视图，零长度合法，非空区域重叠在修改图像前报错。它通过块前缀索引把全部图像交给一个 OpenMP 团队；每个像素仍完成原四级及每级整数舍入。像素数、地址范围和总块数有溢出检查，最后不足八像素的 AVX2 尾部走标量。模型缓存在线程团队创建前准备，像素循环内不做 CPUID 或首次模型分配。

`auto` 仍选择已验收的原 `tetra_avx2`，没有因新候选的单次成绩切换默认。未编入或 CPU/OS 不支持的显式内核请求会报错。无 OpenMP 时 `threads` 的执行上限为 1，JSON 单列 `requested_threads` 和 `openmp_enabled`；OpenMP 动态团队或短输入仍可能少于请求线程数。

预加载 100 张标准图的像素本体为 235,929,600 字节。逐图工作缓冲约为 2,359,296 字节，整批工作缓冲为 235,929,600 字节；批次入口因此用更多内存换取一次团队调度。`model_node_payload_bytes`、`model_runtime_bytes`、`preloaded_image_bytes`、`work_image_bytes` 和每 worker 的块缓冲预算分开报告。模型内存估算不等于进程峰值 RSS，零块缓冲也不表示没有寄存器溢出栈帧或调度元数据。

## 计时与输出预检分离

新命令对列表中的全部图像各映射一次，与正式性能测试分开执行：

```text
jshc verify --competition -l bench.txt -k tetra_avx2 -t 4 --batch -o outputs.raw stage1.slut stage2.slut stage3.slut stage4.slut
```

省略 `--batch` 可验证逐图调度；省略 `-o` 则只输出摘要。原始输出按列表顺序、图像内行优先 RGB8 紧密拼接，无文件头和填充。JSON 包含 `images`、`output_bytes`、`stage_m`、整组 `output_checksum_fnv1a64` 及 `per_image` 的索引、尺寸、字节数和校验值。FNV-1a64 使用标准 offset `14695981039346656037` 和 prime `1099511628211`，以十进制字符串保存，避免 JSON 浮点精度损失；严格比较可对 raw 文件计算 SHA256 或直接逐字节比较。

`verify` 不输出性能成绩，hash 和 raw 写入不进入 `bench` 循环，也不从计时中做事后减法。`bench` 的计算/复制循环保持原样；`--batch` 的单图独立延迟仍为 `null`，每图摊销值不得当作单图实测延迟。严格 100 图对照由统一验收入口核验图像数量、来源、四级模型来源和结果；通用 CPU CLI 本身也可用于较小研究图集。

## 本轮阶段证据

- [R18 CPU 完整验收](../artifacts/r18-progress/ctest-final.json)：六个可用后端通过全色 oracle、不同 m、非均匀网格、四个不同 LUT 的逐级量化链、1/4 线程、短尾和批次混合长度控制。选取的 m 为 17、18、25、26、33，不能误写成所有 17 个合法尺寸逐一全色测试。
- [R18 便携构建验收](../artifacts/r18-portable/acceptance.json)：C++17，AVX2/OpenMP/C++ SIMD/Zig/Rust 全部 OFF；完整 CTest 1/1 通过，3.62 秒。记录全部编译命令和二进制 SHA；[info](../artifacts/r18-portable/info.json) 的默认内核为 `tetra_scalar`，可用内核只有标量四面体和三线性。硬件 AVX2 标志为真不表示该二进制编入 AVX2。
- [早期固定 100 图探索](../artifacts/r18-progress/cpu-benchmark.json)：只是一批 4 线程、每配置五轮的探索结果。它没有交错配对顺序，不能独立支持严格加速比；后续严格比较以统一入口生成的新证据为准。
- [CPU 实现与故障修复说明](r18-cpu.md)：记录 MinGW Win64 按值向量聚合栈对齐故障、引用传递修复及保留的原始失败证据。

便携构建存在原有 `fit_r14.cpp` 的一个无 OpenMP 未使用参数警告；构建和门禁均成功。未为此与当前范围无关的警告改动拟合器，也未宣称未经实测的跨平台性能。
