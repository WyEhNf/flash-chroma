# R37：Windows 报告发布故障与零像素重跑恢复

R29 第二个并行工作块中的回归进程实际因 `PermissionError / WinError 5` 停止。它已经完成 endpoint_corner/m25/trilinear 的原生完整 RGB 映射、统计及隔离账本提交，但替换 `regression.json` 时失败，因此阶段索引缺少这一条结果。开发、校准进程继续运行；失败进程没有被描述为成功。

## 持久化修复

新的 `lutlab.reportio.write_report` 保留同目录临时文件及原子替换。只对 Windows 5/32/33 的共享/访问冲突作有界退避重试，最长五秒；超过预算或其他异常仍抛出，不退化为截断原文件，也不隐藏失败。读取辅助函数在解码和 JSON 解析前先关闭文件，缩短占用时间。非法 JSON 的临时文件也会清理。

集中实机检查通过：强制持有拒绝删除共享的 Windows 文件句柄，使旧 `os.replace` 失败；新写入器观察到五次冲突，在释放句柄后成功发布。随后验证旧读取副本保持完整、新路径读到完整新版本，以及 NaN 拒绝时没有留下目标或临时文件。没有运行拟合或 RGB 映射。

初版检查曾假设 `FILE_SHARE_DELETE` 足以允许持有读句柄时使用当前替换方式；本机实测拒绝，失败驱动及模块原字节保留在 `15e8cda1c124/`，没有执行恢复。修订后不再依赖这个假设，而采用短读者和有界写入重试。[Microsoft 的重命名规则](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information)区分普通替换与允许替换已打开目标的 POSIX 标志；本项目没有新增低层 POSIX 重命名实现。

## 已完成结果的恢复

恢复工具先以操作系统进程状态确认回归写入者确实终止，并要求原控制器仍活着且记录该子进程失败。工具核验冻结源码镜像、四张原表、真值、模型、执行文件、底层完整域结果及隔离账本中已提交的观测 ID，再用临时验证账本检查现有合同。

只有这些证据都通过，才备份旧阶段索引并补入遗漏条目。成功恢复 **1 条** `endpoint_corner-mild-s0-849e9bb7/trilinear/m25`；像素重执行次数为 **0**。原控制器随后实际将该条目导入总账本。没有绕过其总账本写入租约，也没有将失败子进程状态改为成功。

完成证据为 `artifacts/r37-report-io/854f23403dda/stage.json`；恢复前原始阶段索引、实际错误日志哈希、旧/新索引哈希、观测来源及源码指纹都保留。该阶段不证明整个矩阵完成。

## 后续调度的边界

新增 `scripts/r38_parallel_phases.py` 与 `r38_frozen_worker.py`，待当前控制器退出后使用。它们保留原始 R29 数值拟合源码与公共缓存身份，只在进程内为 JSON 发布加载明确记录哈希的 I/O 层；阶段报告会另列 `execution_io_overlays`，不将它隐瞒在旧源码标记里。当前尚未实际启动这一新调度器，不能把语法检查写成运行验收。

新调度器还要求留出阶段同时具备基线规则和基线/扩展联合冻结规则，防止在 R36 开发、校准完成前提前暴露相同留出源。原来的 5400 项与新增 2517 项分母保持不变。没有创建 subagent。
