# 修订90：显式非连续批处理接口

新增显式 `jshc_cc_apply_to_segments`，让调用者直接提交独立RGB8源/目标图像，一批共享任务分派。两条固定链各完整16,777,216色与87标量零字节差，拟合精度逐色保持。已有单段、原地接口及完整prepare路径不自动切换。

正式三角色36场景中，新接口对旧87逐图有29个控制有效场景，最劣吞吐保留81.7993%（80档）；对同场旧87整批有26个有效场景，最劣保留93.1745%（90档）。另7/10个比较控制失效，全部保留，不能纳入全场保证。有效收益主要是非连续输入避免打包回写，以及相对逐图共享调度；连续图像与已有整批入口接近，不称击败所有已有最佳路径。

## 新入口与成本合同

```c
int jshc_cc_apply_to_segments(void* handle,
    const uint8_t* const* sources, uint8_t* const* destinations,
    const size_t* bytes, size_t count, int kernel, int threads,
    char* error, size_t error_bytes);
```

显式0～100个紧密RGB8段，可不等长；空批允许空数组，空段允许空指针。非空目标必须与所有源和其它目标不重叠，重复只读源允许。同址映射继续使用旧单段入口。所有长度/范围溢出/交叉重叠验证、指针快照、任务构造与分配均在新入口内部，验证失败不得写任何图像。

每段以最多65,536像素切块，将整批任务一次 `parallel for schedule(static)`；并行嵌套时使用一个worker。direct路径复用已有pair48/linear真分离核，非整8尾部复制后用标量；fallback每块复制并调用相同旧核的单线程分支。没有修改模型、插值式、调色板或AVX2像素TU，也没有引入AVX512。

标准百图为1,200个任务，每个Task在本机为24 B，有效载荷请求28,800 B；另100段快照2,400 B。allocator额外开销、stack其它变量及容器capacity实现余量未量峰值，不能把这些逻辑字节当RSS。新增API每次构造任务并分配的成本完整计时，未移到计时外或返回后的后台。原生模型容量direct 18,579,204 B、fallback 1,852,824 B，与87相同。

## 冻结三角色与布局

- 角色0：旧87原生逐图调用；循环在C++，不计Python逐图桥接。
- 角色1：旧87单次连续bulk；布局0直接使用与另外两者相同的源/目标地址。布局1每内轮完整pack源、旧bulk映射、scatter回实际独立目标，scratch预分配。
- 角色2：新90显式segments；同布局实际源/目标指针与角色0相同，包含API自身全部验证、任务构造/分配、调度和映射。

布局0为连续缓冲，布局1为真实每图独立分配的源/目标。不得跨布局取绝对时间相除。benchmark为了同时提供布局1的bulk适配镜像，连同预载frames最大约1.2 GB，这不是产品API新增模型容量。原始记录提供fixture逻辑字节和分配后RSS快照，未宣称峰值RSS或产品内存减少。

性能计划 `experiments/p16-segment-performance-v1.json` SHA `0f0e547cea09a410bb719facf7599c8e98c6caa80d4532a5ee5ae0d3e0645129`。四个新进程角色顺序012/210/120/021，每对先后各两次，未覆盖全部六排列，不称完整位置平衡。线程、布局、模型与N顺序事先交替。direct全尺寸1024×768及同源二倍降采样512×384，ordinary fallback全尺寸；N1/10/100，各角色warm2，正式和独立A/A各64/16/5内轮。

A/A范围事先0.85～1.15，不追授历史探针较宽范围。组内中位→同进程配对→四比中位；档位按最劣进程吞吐倒数；“无明显退化”为中位时间比≤1.05、任一进程≤1.10。prepare、文件读取/解析、照片解码、fixture分配在稳态外，与已单独验收的87完整prepare成本不混合。没有删轮或失败后重跑。

## 身份、可移植性与复核

90 DLL SHA `8520ed20f891a66669c282ac23d3fd51175eb93a33ba03d0eddd384d52894825`；独立C++三角色driver SHA `04d9cba8e3073306fb15e013b5ef2e893ee16424de60f56d35b0289e610d8ff3`；87基线 SHA `58591a725d367dce3713ff88af4d5549afea5af1ac4f3a39284443586893c158`。driver不链接像素核或OpenMP，通过同进程两个DLL函数指针调用，避免另造较劣像素基线；90编译布局及新任务访问也可能影响结果，时间差不能叫纯fork/join成本。

实测Windows11/AMD Ryzen9 8945HX/GCC15.2，仅AVX2/BMI1像素核，无AVX512。进程allowed CPUs `[0,2,4,6]`，未验证每个OpenMP TID单核落点，无锁频控温；不是题面Intel机器实测。四新进程顺序运行，root/tail/memory全程静默，无并行编译、JIT、ZIP或Git。入口使用C ABI、C++标准容器/OpenMP，本阶段只验证Windows x64，未称Linux/无AVX2硬件已验证；分配失败未故障注入。

源码与实际编译flags/link、质量及性能全原始轮次归档 `report/data/p16-segment-batch-v1/`，包括失败A/A和历史执行依赖CRLF/Git LF双身份。复算不加载DLL、不追加性能：

```powershell
python -X utf8 scripts/audit_p16_segments.py report/data/p16-segment-batch-v1/raw-evidence.zip
```

新增接口继续保持显式调用。已有连续数据优先使用已经验收的bulk边界；非连续用户可选择segments，需按这里相同模型/形状/线程的有效证据评估。未把旧诊断bulk的收益冒充新API，也不把准备或模型共享收益混入本场稳态。
