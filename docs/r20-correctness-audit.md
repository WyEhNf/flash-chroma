# R20：图片执行路径验收与裁剪场景容量检查

日期：2026-10-15。按当前目标串行推进。待认证的 Git 推送已取消，远端仍为 `7059bc7`；本轮修改未推送。

## 正确性缺口及修复

原 `validate` 通过原生 `cube` 生成全色映射，再用 Pillow 读取图片并查该表计算误差。这可以验证稀疏映射的数值，却没有执行原生图片路径。特别是 Pillow 会把部分 16 位 RGB PNG 解码成 `RGB`，仅凭 `mode == RGB` 不能证明源文件是 RGB8，可能错误报告满足图片输入规格。

现在 `validate` 先实际运行所选后端的图片路径，获取按列表顺序拼接的全部 RGB8 输出，再执行全色映射。逐图检查输出长度，并将实际输出与该图输入逐像素查全色映射的结果逐字节比较；不一致、缺字节和多余字节都会报错。质量统计使用实际图片输出。报告新增图片执行命令、`image_execution_verified` 和 `mapped_images_sha256`。

CPU 使用 `verify`。CUDA 的原生 `verify` 仍要求恰好100张标准图片，小图集由已有 `apply` 逐图执行；该回退同样调用 CUDA，保存每条命令，不替换后端。比赛模式的原生解码器负责检查源位深与通道数。非比赛 CPU 入口未检查源位深时，不再声称已证明提交格式合同。

`accept --backend both` 现在同时核对 CPU/CUDA 全色和实际图片输出 SHA。原有阈值口径保持显式：示例 `mean < 2` 仍不等价于逐像素通过或官方验收。

## 集中阶段验收

只运行一次串行批次，完整耗时 **202.19秒**：

- 11项 Python 检验全部通过，13.46秒。扩展现有进程级检验，确认真实16位RGB PNG被比赛入口拒绝，模拟的图片输出损坏会被发现，异常路径的Windows临时文件可清理。
- 复用R19的六组冻结模型，分别实际执行CPU/CUDA的100图和全16,777,216颜色。每组图片输出逐字节等于全色映射查表；两个后端的整组图片与全色SHA均一致。六组的逐图统计、全色统计、全色SHA及示例门禁结论与原R19记录完全相同。
- 对一个标准帧实际执行CUDA的`apply`回退，输出与全色映射一致。
- 预先固定增加`clip-7`的m25和m33两个容量候选，方法仍为DP网格和分层LS；没有进行尺寸全扫。两组也完成上述100图与全色的双后端核验。

本轮未修改C++/CUDA映射源码，也未更换二进制。既有独立64位oracle的完整CTest和R19严格配对性能证据继续保留；未将验收耗时当作映射速度，也未因为验证器增加I/O而重跑112次性能比较。

## 容量检查没有解决最大误差

以下为同一已知`clip-7`输入的后续比较，不称为新盲测：

| 17 | 75,196 | 1.483448 | 6.082763 | 34.000000 | 2.230224 | 失败 |
| 18 | 86,272 | 1.408871 | 6.000000 | 26.000000 | 1.826548 | 通过 |

| 33 | 448,252 | 1.298662 | 5.744563 | 27.294688 | 1.477005 | 通过 |

m25改善平均误差，却将全色max恢复到34；m33的平均误差又劣于m25。因此这两组都不能代替最大误差门禁，也不据此修改默认模型策略。m25/m33本次完整四表拟合分别耗时2.121/2.908秒，只是功能批次中的单次离线拟合记录。

对已测热点逐级追踪发现：m17、m18和m25的首个最大误差热点，单独以稀疏第一级替换精确第一级、后续保留完整表时，最终ΔE分别为37、27和34；第一级误差的后续放大值得优先处理。m33的首个热点则在第二级出现明显误差：精确输入`[0,175,169]`应输出`[0,223,216]`，稀疏输出为`[0,233,208]`。这说明仅增加节点不能保证拟合稳定，下一步需要检查输入边界上的采样覆盖及拟合条件。单级替换诊断不能相加，不能作为全局误差贡献的证明。
